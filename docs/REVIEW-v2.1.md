## A. 审计与时间

### P0-1 锁定时间取自 git 提交时间，可以伪造

- **严重程度**：P0
- **为什么**：v2.0 用「第一次添加该文件的 git 提交时间」作为锁定时间。可是 GitHub 写文件接口的 `committer` 参数允许客户端自己填 `date`（官方文档列出了这个字段），提交时间可以任意倒填；持有写权限令牌的人还能强制推送，改写历史。这个实验要防的正是「事后修改」，审计证据不能由被审计的人自己写。
- **当前设计**：`serverLockedAt` = `git log --format=%cI` 取到的第一个提交时间；仓库没有开启分支保护。
- **建议修改**：
  1. 锁定时间改由 GitHub 服务器产生，客户端填的时间只作参考：
     - 推荐路线：用 GitHub Issue 提交（见 P1-1），锁定时间取 `issue.created_at`，这个时间由服务器生成，无法倒填；
     - 备选路线：继续用令牌直接写文件，但由一个「公证」工作流在收到推送后，从 GitHub 事件接口读取这次推送的服务器时间（`PushEvent.created_at`），写入锁定记录。
  2. 每份预测计算 `predictionHash`（规范化 JSON 的 SHA-256），和 `commitSha`、`snapshotId` 一起写进**独立的锁定记录**。第一份锁定记录生效，之后的任何改动都只会被标记为「已改动」，计分始终按第一份。
  3. 给 `main` 分支开启保护：禁止强制推送、禁止删除分支。
  4. 不再宣称「不可篡改」，改为「可审计」：服务器时间 + 哈希 + 只新建不覆盖 + 分支保护，四样证据组合起来。
- **是否必须修改**：是
- **修改后的 Schema**：
```json
// data/locks/2026-10-08/user.json（公证工作流写入，只新建）
{
  "date": "2026-10-08", "predictor": "user",
  "clientSubmittedAt": "2026-10-08T08:35:00+08:00",
  "serverLockedAt": "2026-10-08T08:35:07+08:00",
  "serverTimeSource": "issue.created_at",
  "issueNumber": 12,
  "commitSha": "9f3c…",
  "predictionHash": "sha256:4b1e…",
  "snapshotId": "2026-10-08/morning",
  "deadline": "2026-10-08T09:15:00+08:00",
  "onTime": true
}
```
- **代码现状**：存在此问题。

### 时间字段定义（确认无误，补一条约束）

| 字段 | 定义 | 谁写 | 可否修改 |
|---|---|---|---|
| `dataTime` | 数据对应的时间，例如美股 10-07 收盘 | 快照 | 否 |
| `cutoff` | 理论上最早可获得的北京时间 | 快照（按规则计算） | 否 |
| `fetchedAt` | 系统实际抓取时间 | 快照 | 否 |
| `serverLockedAt` | 服务器确认收到预测的时间 | 锁定记录 | 否 |
| `availableAtLock` | `cutoff <= serverLockedAt`，**只在读取时计算，不落盘** | — | — |

补充约束：`cutoff` 的取值规则必须**保守**（宁晚勿早），并写进配置、带版本。v2.0 采用的规则：A 股 15:00；港股 16:10；美股为美国交易日次日北京时间 05:00（夏令时实际 04:00 就能拿到，取 05:00 更保守）；普通基金净值当天 21:00；QDII 净值为下一个 A 股交易日 21:00。v2.0 已经符合「`availableAtLock` 不落盘」（P1 修订意见第六条），无需再改。

### P1-4 定时任务延迟、push 触发的运行，会在错误时间生成批次

- **严重程度**：P1
- **为什么**：GitHub 官方文档说明：定时任务在高负载时会延迟，负载足够高时排队的任务可能被丢弃；公开仓库 60 天无活动，定时任务会被自动停用。v2.0 只按「当前是上午还是下午」决定生成哪个批次：
  - 22:13 的任务如果拖到 0:30，`today` 变成第二天，会给后天提前生成一个「晚间批次」，等真正的晚间任务运行时发现文件已存在，直接跳过，于是这个批次缺少当天收盘数据；
  - 我推送代码会触发一次运行（比如下午 13:00），也可能提前占掉当晚的晚间批次。
- **当前设计**：只按上午 / 下午区分批次；`writeOnce` 保证不覆盖，但不能保证在正确的时间生成。
- **建议修改**：
  1. 每个批次规定时间窗口：晚间批次 21:30–23:59，早间批次 07:30 到截止时间。窗口外的运行只做结算，不生成批次。
  2. 批次目标日期按时间窗口计算，不再用 `today + 1` 推算。
  3. 加补偿定时：22:43、08:27 各再跑一次，靠幂等保证不重复生成。
  4. 每个批次文件写入 `runId`、`trigger`（schedule / push / 手动）和实际生成时间，便于审计。
  5. 每周自动提交一次心跳，防止定时任务因 60 天无活动被停用。
- **是否必须修改**：强烈建议
- **修改后的流程**：`batch = window(now)`；`target = window === 'evening' ? nextTD(today) : today`；`if (!batch) settleOnly()`。
- **代码现状**：存在此问题。

### P1-5 AI 和基准的批次可能晚于你的锁定时间

- **严重程度**：P1
- **为什么**：如果早间任务延迟到 9:10 才运行，而你 8:35 已经锁定，当天拿来和你对比的 AI、基准就比你多看了 35 分钟信息。这对你不公平，也违反「AI 必须在用户锁定之前生成」。
- **当前设计**：计分时按「早间 → 晚间 → 提前」的顺序取第一个存在的批次。
- **建议修改**：计分时只用 `asOf <= min(serverLockedAt, deadline)` 的最新批次。你缺席的日子，用 `asOf <= deadline` 的最新批次。所有批次都保留，从不重新生成。
- **是否必须修改**：强烈建议
- **代码现状**：存在此问题。

## B. 公平性与基准

### P0-4 你比基准多看 78 分钟信息，包括 9:15 集合竞价

- **严重程度**：P0
- **为什么**：基准、规则模型和 AI 的信息截止在 08:07，你可以在 09:25 前随时提交。A 股 9:15–9:25 是集合竞价，能看到大部分股票和板块的虚拟开盘价，这对当天涨跌有很强的提示作用。这样比出来的「我比基准强」，可能只是因为你看到了竞价。这是最需要提防的自我欺骗来源。
- **当前设计**：截止时间 09:25，基准快照 08:07。
- **建议修改**（二选一）：
  - **方案 A（推荐）**：截止时间改为 **09:15**，在集合竞价之前，并在规则里明确「不使用竞价信息」。早间批次 08:07 仍然生效。
  - **方案 B**：保留 09:25，但在 09:20 增加一个「竞价批次」，让基准和 AI 也拿到竞价数据。缺点是定时任务延迟很常见，09:20 的批次经常赶不上，公平性没有保障。
- **是否必须修改**：是。需要你在 10-08 之前选定一个方案。
- **代码现状**：存在此问题。

### P1-7 外盘基准只有 β 版本，缺原始跟随；0% 混进了方向排名

- **严重程度**：P1（修订意见已列为必须修改）
- **为什么**：β 是在研究集上拟合出来的，已经算一个统计模型，不是「最笨的办法」。`bench_zero` 永远预测平，方向命中只取决于当天是不是平盘，不应该参加方向比较。
- **当前设计**：只有 `bench_us = a + b × 外盘`，而且带截距 a（截距本身就是研究期的平均涨幅）；统计里把 `bench_zero` 也算进了方向比较。
- **建议修改**：
  - `bench_external_raw`：预测值 = 外盘累计涨跌。不拟合，不带截距。
  - `bench_external_beta`：预测值 = β × 外盘累计涨跌。**不带截距**，β 只在研究集上拟合，随规则版本冻结。截距会把「研究期是牛市」这个信息带进来，不属于外盘跟随。
  - 每只基金对应哪个外盘写进配置并带版本，例如 QDII 对应纳指100，其余对应费城半导体，国寿可以改成纳指100。
  - **最佳方向基准**：只在 raw、beta、昨日延续三者中选。**最佳 MAE 基准**：四者（加上 0%）中选 MAE 最低的。
  - 「选最好的那个基准来比」对你是更严格的标准，不会偏向你，可以保留。
- **是否必须修改**：是
- **修改后的 Schema**：

### P2-2 规则模型的截距等于研究期平均涨幅

- **严重程度**：P2
- **为什么**：v1.0 的拟合结果是截距 0.70、斜率很小，没有信号触发时，模型每天都预测 +0.67%，实际上就是「永远看涨」。研究期正好是上涨行情，换到下跌行情会系统性出错。

- **是否必须修改**：MVP 可暂缓，建议和 P1-7 一起改。

## C. 统计学

### P0-2 5 只基金同一天高度相关，被当成 5 个独立样本

- **严重程度**：P0
- **为什么**：你这五只基金同涨同跌的程度很高，同一天的 5 条观测，信息量接近 1~2 条，而不是 5 条。v2.0 的 bootstrap 和信号的 Wilson 区间都把每条观测当成独立样本，会让置信区间窄 √2~√5 倍，于是**更容易误报「显著」**。信号也一样，例如「纳指涨超 1%」一触发就是 5 只基金同时触发，等于同一天被重复计数了 5 次。
- **当前设计**：`bootDiff` 逐条重抽样；`sigStats` 按「日 × 基金」计数，再算 Wilson 区间。
- **建议修改**：
  1. **配对比较按日聚类**：先算出每天的差值（该日 5 只基金误差差的平均），再对「日」做重抽样，得到 95% 区间；同时做一次按日的符号翻转置换检验，给出 p 值。
  2. **方向配对**：每天统计「我对 / 基准错」和「我错 / 基准对」的条数差，再按日聚类做 bootstrap 和置换检验，不直接比较两个百分比。
  3. **信号统计**：样本数报两个，「观测数」和「独立交易日数」。Wilson 区间用有效样本数：n_eff = 观测数 ÷ 设计效应，设计效应根据同日的组内相关系数估计；简单做法是直接按交易日聚合后再算。
  4. 成绩页同时写明「有效观测样本」（日 × 基金）和「交易日数」。
- **是否必须修改**：是
- **修改后的 Schema**：
```json
// stats.json 中每个对比
"user_vs_bench_external_beta": {
  "obs": 160, "days": 32,
  "mae": { "user": 0.61, "bench": 0.67, "improvePct": 8.9,
           "dayClusterBootstrap95": [-0.02, 0.13], "signFlipP": 0.21 },
  "direction": { "user": 57.8, "bench": 54.2, "liftPP": 3.6,
                 "wins": 21, "losses": 15, "dayClusterBootstrap95": [-2.1, 9.4], "signFlipP": 0.33 }
}
```

### P0-3 每天看一次显著性 + 多个对比，会制造假阳性

- **严重程度**：P0
- **为什么**：
  1. **反复查看**：成绩页每天重新计算「是否显著」。只要每天都看，即使真实能力为零，某一天碰巧越过 5% 门槛的概率也会远高于 5%；一旦看到「显著」就停下来，结论就是假的。
  2. **多重比较**：一次和 4 个基准加 2 个对照组比较，只要有一个显著就宣布胜利，假阳性率会成倍上升。
- **当前设计**：每天计算；没有校正。
- **建议修改**：
  1. **事先登记主要结论**（写进 `config.json` 并带版本，之后不能改）：
     - 主要终点 1：MAE，与「最佳 MAE 基准」做按日聚类的配对检验；
     - 主要终点 2：方向，与「最佳方向基准」做同样的检验；
     - 两个终点用 Holm 校正，整体 α = 0.05。
  2. **固定评估节点**：只在第 60、120、200 个交易日给出正式结论；中间只显示数字和区间，结论区写「未到评估节点」。如果想每天都看，就改用序贯检验并分配 α（例如 O'Brien–Fleming 边界）。
  3. 「100 个观测」只是开放结论区的产品门槛，不代表统计上够用。
  4. 其余对比（vs 规则模型、vs AI、分基金）一律标注为「探索性」，不允许写「显著优于」。
- **是否必须修改**：是
- **修改后的 Schema**：
```json
// config.json 增加（登记后冻结）
"preregistration": {
  "registeredAt": "2026-10-07",
  "primary": [

    { "id": "DIR", "against": "best_direction_benchmark", "test": "day_cluster_signflip" }
  ],

}
```

### P1-3 信号的「有效」判定没有多重检验校正，也没有防抖

- **严重程度**：P1
- **为什么**：现在有 20 条信号，每天都重新判定一次「有效 / 失效」。按 5% 显著性，即使全部是噪声，长期下来也会有信号偶尔被判成「有效」。在门槛附近的信号还会来回跳状态。
- **建议修改**：
  - 对所有信号做 Benjamini–Hochberg 校正，控制错误发现率在 10%；
  - 状态切换加防抖：连续 5 个交易日满足条件才转为「有效」或「失效」；
  - 「有效」还要求独立交易日数 ≥ 20（不只是观测数 ≥ 20）。
- **是否必须修改**：强烈建议

### P2-1 三态命中率对谨慎预测不友好，需要补充指标

- **严重程度**：P2
- **为什么**：三态要求完全一致。你预测 +0.05%（判为平），实际 +0.8%，算错；预测 +0.2%，算对。这会鼓励「为了方向而硬给方向」，也会让 raw 外盘基准在小波动时大量判为平。
- **建议修改**：主指标保持三态（已定）；另外显示两项辅助指标：
  - 出手率：预测不是平的比例；
  - 出手准确率：预测不是平、实际也不是平的观测里，方向猜对的比例。
- **是否必须修改**：可暂缓

## D. 过拟合与 AI

### P1-2 留出集每天滚动重复使用，复盘提出的新规则还看过留出集里的日子

- **严重程度**：P1
- **为什么**：
  1. 留出集是「最近 40 天」，每天往前滚一天，同一批日子会被反复拿来做判定，慢慢就变成了训练数据。
  2. 每天复盘时，AI 看着当天的实际结果提出新规则。当天正好属于留出集，所以这个规则是「看过答案」后提出的，再拿留出集去验证，等于自己考自己。
- **建议修改**：
  - 每条信号、每个模型版本都记录 `proposedAt`；
  - **它的样本外证据只能来自 `proposedAt` 之后的日子**（前向验证）。研究集回测只用来做初筛；
  - 由复盘提出的新信号，状态从「实验中」起步，至少积累 20 个**提出之后**的交易日，才能进入「待验证」；
  - 研究集和留出集的切分改为固定锚点，每季度重切一次并记录版本，不再每天滚动。
- **是否必须修改**：强烈建议

### P1-6 先看到 AI 草稿再预测，「我的判断」被 AI 锚定

- **严重程度**：P1
- **为什么**：如果你先看 AI 草稿，再「带入、微调」，统计出来的其实是 AI 的能力，「我会不会预测」这个问题就答不了。修订意见允许 AI 提供参考草稿，但必须能测量你对它的依赖程度。
- **建议修改**：采用「先独立判断，后看草稿」的两步流程：
  1. 第一步：只显示数据快照和触发的规律，你填写 5 个数值，生成 `initial`（不提交、不锁定，只保存在本次提交里）；
  2. 第二步：显示 AI 草稿，你可以修改，最终数值为 `final`，只有 `final` 参与正式计分；
  3. 同时记录 `initial` 与 AI 的差异、`final` 与 `initial` 的差异，以后统计「看了 AI 之后，我是更准还是更差」。
  4. 去掉「一键带入 AI 草稿」按钮。
- **是否必须修改**：强烈建议。需要你确认是否采用这个流程。

### P1-12 缺依据完整性指标和 AI 版本字段

- **严重程度**：P1
- **建议修改**：
  - 锁定时自动生成依据计数：数据依据、有效信号、今天未触发、历史无效、疑似事后信息。复盘发现疑似事后信息后，只追加审计标记 `suspectedHindsight`，不改原预测；
  - 每份 AI 草稿记录 `modelName`（实际调用到的模型，可能因额度降级）、`promptVersion`、`aiVersion`、`generatedAt`、`snapshotId`；成绩按 AI 版本分组统计。
- **是否必须修改**：强烈建议
- **修改后的 Schema**：
```json
"evidence": { "dataRefs": 3, "validSignals": 2, "notTriggered": 1, "historicallyInvalid": 0, "suspectedHindsight": 0, "subjectiveOnly": 1 },
"ai": { "modelName": "gemini-3.6-flash", "promptVersion": "draft-2", "aiVersion": "2026.10.07", "generatedAt": "…", "snapshotId": "2026-10-08/morning" }
```

## E. 数据与版本

### P1-8 信号定义和每日状态写在同一个文件里，每天被改写

- **严重程度**：P1
- **为什么**：`signals.json` 每天被定时任务整体重写。定义（`when`、`vote`）和统计、状态混在一起，事后很难证明某条规则的条件没被悄悄改过。规则模型引用的又是当前的定义，旧版本模型的行为也会跟着变。
- **建议修改**：
```
data/signals/
├── definitions/R017.json        // 只新建；改条件 = 新建 R017.v2
├── status/2026-10-08.json       // 每天的状态与统计快照（只新建）
└── changelog.json               // 状态切换记录（只追加）
data/models/v1.0.json            // 引用 "R017@v1" 这样带版本的定义
```
- **是否必须修改**：强烈建议

### P1-9 历史行情每次重新下载，数据商修订后统计不可复现

- **严重程度**：P1
- **为什么**：每次运行都重新下载 1~2 年的行情来算信号统计。Yahoo、天天基金偶尔会修订历史数据或复权口径，过去的统计会悄悄变化，无法复现。
- **建议修改**：每天把新抓到的数据点追加到 `data/market/{序列}.jsonl`（只追加）。统计和回测只读本地数据；发现数据商的历史值与本地不一致时，记录一条修订，不覆盖。
- **是否必须修改**：强烈建议

### P1-10 历史交易日历缺 2025 年节假日，回测因子算错

- **严重程度**：P1
- **为什么**：`calendar.json` 只有 2026 年的节假日。回测 2025 年的数据时，会把春节、国庆等假期当成交易日，「上一交易日」和「隔夜外盘累计」都会算错，进而影响信号统计。
- **建议修改**：历史交易日直接取上证指数实际有数据的日期，未来交易日才用日历。
- **是否必须修改**：强烈建议

### P2-3 净值更正直接覆盖结果文件

- **建议修改**：结果文件改为 `results/{日期}/v1.json`、`v2.json`…，每个版本记录数据源、更正时间和原因；统计使用最新确认值，审计保留全部版本。
- **是否必须修改**：可暂缓

### P2-6 机器人和人工都在改 `funds.json`

- **为什么**：持仓金额是机器人每天滚动写入的，加减仓时你又要手工改，两边会冲突。
- **建议修改**：拆成 `funds.json`（基金定义，人工维护）和 `state/holdings.json`（机器人写）。加减仓记录为 `holdings/trades.jsonl`（只追加）。

### P2-7 数据规模（1~2 年）

估算：每个交易日约 25 个文件、60 KB；一年约 250 个交易日，即 6,000 个文件、15 MB；两年约 30 MB。git 和 Pages 都没有压力。App 只读汇总文件和当天文件，性能没问题。唯一需要注意的是「统计每次全量重算」，两年后结果文件约 500 个，仍在一秒内完成。**结论：JSON + git 足够用 2 年以上，不需要换数据库。**

## F. 安全

### P1-1 手机浏览器保存的写权限令牌，和你其他 Pages 站点同源

- **严重程度**：P1
- **为什么**：
  1. 你的所有 GitHub Pages 项目站点（Game-On、Forge、Fund-diary）都在 `zxy8125ss.github.io` 这一个源下。浏览器的 localStorage 按源隔离，不按路径隔离，所以这几个站点里任何一个页面的脚本，都能读到基金日记保存的令牌。Game-On 会展示外部抓来的内容，一旦出现 XSS，令牌就会泄露。
  2. 令牌有仓库写权限，泄露后别人可以改写预测数据（虽然改不了工作流文件，那需要单独的 workflows 权限）。
  3. 令牌本身还可以用来倒填提交时间（见 P0-1）。
- **当前设计**：fine-grained 令牌，只对本仓库开放 Contents 读写，保存在 localStorage。
- **建议修改**（推荐 A）：
  - **方案 A：用 GitHub Issue 提交，浏览器里不存令牌。** App 生成预测内容，打开一个预填好的「新建 Issue」页面，你在 GitHub 网页上点提交即可（使用你在浏览器里的 GitHub 登录状态）。由工作流 `on: issues.opened` 完成以下事情：校验作者是你本人 → 用 `issue.created_at` 作为服务器锁定时间 → 校验截止时间 → 计算哈希 → 写入预测文件和锁定记录 → 关闭 Issue。修正意见用 Issue 评论提交，同样带服务器时间。
    - 优点：不存令牌；锁定时间无法伪造；顺带解决 P0-1。
    - 代价：提交时要跳到 GitHub 网页，多点一次；手机浏览器需要保持 GitHub 登录。工作流在几十秒内完成写入，App 先显示「已提交，等待锁定」。
  - **方案 B：继续用令牌**，加以下缓解：令牌设 30 天有效期；用你设的 PIN 加密后再存储；配合公证工作流（P0-1）。只能降低风险，消除不了同源问题。
- **是否必须修改**：强烈建议。需要你确认用哪个方案。
